# Windows 7×24 无人值守“机器人员工”设计

> 文档性质：设计 + 阶段 0.5 已落地的 ChatCut 健康检查实现（macOS）。
> 设计日期：2026-10-17。  
> 自动化边界：完整执行到“本机交付”；第 07 步发布继续由员工手动完成，系统不得登录发布账号、上传或发布。

## 1. 现状与差距

### 1.1 审阅范围与结论

本设计基于项目现有文档与实现，包括 **AGENTS.md**、**PROJECT_STATE.md**、**README.md**、**docs/Windows源码部署.md**、**docs/客户交付-流程与耗时现状.md**、**docs/employee/pipeline.md**、**docs/modules/*.md**、**skills/team-video-workflow/SKILL.md**，以及 **workflow/cli.py**、**workflow/api.py**、**workflow/mcp_server.py**、**workflow/orchestration/*.py**、**workflow/production/chatcut.py**、**workflow/production/preparation.py**、**scripts/prepare_chatcut.py**、**scripts/run_local_batch.py**、**workflow/platforms/*.py**。

现有项目已经具备“可恢复生产流水线”的重要基础，但还不是一个能够在客户 Windows 电脑上长期自治运行的守护系统。现状应按“已有、部分已有、需新建”区分，避免重复建设或错误宣称无人值守已经完成。

| 能力 | 现状判断 | 依据与设计含义 |
|---|---|---|
| 任务入口 | 已有多种程序入口，未形成无人值守收件箱 | **workflow/cli.py**、**workflow/api.py**、**workflow/mcp_server.py** 可复用为控制面入口；需新增稳定的任务收件箱协议和监听器 |
| 流水线编排 | 已有 | **workflow/orchestration/pipeline.py**、**local.py**、**process.py** 已承担阶段编排、进程执行和本地路线；无人值守层应调用它们，不重写业务流水线 |
| 互斥与防重入 | 已有基础 | 现有 pipeline_lock 语义必须保留；需补充锁租约、持有者信息、心跳和陈旧锁判定，不能简单删除锁文件 |
| 哈希复用 | 已有 | 已成功步骤和素材结果按证据哈希复用；新调度器必须把输入哈希、配置哈希、工具版本和输出哈希纳入幂等键 |
| 逐条恢复 | 已有基础 | 现有 stage-state／逐条状态是恢复核心；需增加跨重启的 next_retry_at、attempt、worker_id、last_heartbeat、degraded_reason |
| 批准证据 | 已有 | pipeline-evidence 与 zh-approval 规则是批准事实来源；新系统只能引用真实证据，不能为消除阻塞伪造“用户已批准” |
| 本地批量制作 | 已有降级路线 | **scripts/run_local_batch.py** 提供 FFmpeg 本地批处理能力，可作为标记清楚的降级方案，不应成为默认剪辑器 |
| ChatCut 准备 | 已有部分能力 | **workflow/production/chatcut.py**、**workflow/production/preparation.py** 与 **scripts/prepare_chatcut.py** 可准备／校验编辑批次；当前 prepare_chatcut.py 生成的是 validateOnly 编辑批次，不能等同于真实编辑和导出 |
| ChatCut 真正执行 | 依赖交互式执行端 | 真实编辑与导出目前由交互式 Windows 会话中的 ChatCut Desktop 执行，实际操作者是员工或 Codex 已连接的 ChatCut 工具／MCP；Python 流水线本身不是无头 ChatCut 渲染器 |
| 健康检查与自愈 | 不完整 | 需新建 ChatCut 会话探针、弹窗检测、自动重启、退避、金丝雀导出和版本兼容检查 |
| 定时与事件唤醒 | 需新建 | 当前项目不是长期驻留的 Supervisor；需新增任务计划、目录监听和启动恢复 |
| 批准队列与通知 | 需新建 | 现有证据规则解决“什么算批准”，但未解决批量提醒、超时升级、回执关联和通知失败恢复 |
| 预算与日报 | 部分文档化 | 已有流程耗时和计时口径；需新建机器可执行的单任务／每日成本与时长上限、日报聚合和熔断器 |
| 发布 | 明确排除 | 第 07 步保持员工手动。无人值守系统不得接触 TikTok、紫鸟、邮箱等发布账号，也不得扩大文案批准所授予的权限 |

### 1.2 核心差距

1. **缺少长期控制面**：现有流水线更像“被调用的一次性任务”，缺少 7×24 Supervisor、心跳、任务租约、跨重启恢复和每日运维闭环。
2. **ChatCut 尚非可证明的无头执行器**：validateOnly 能证明批次结构可接受，不能证明 GUI 已完成编辑、字幕、包装和导出；无人值守必须新增可观测的 ChatCut 控制适配器。
3. **批准可能无限等待**：现有证据规则严谨，但缺少通知队列、SLA、超时提醒、可配置自动批准范围和“不批准也不丢任务”的状态。
4. **安全边界未产品化**：codex exec、素材采集、TTS 和桌面自动化需要独立 Windows 账号、最小目录权限、网络白名单、预算熔断和明确禁止发布／付费越权。
5. **FFmpeg 降级缺少治理**：必须区分“ChatCut 成片”和“FFmpeg 降级成片”，记录触发原因、差异、审批策略和恢复到 ChatCut 的条件。

## 2. 总体架构

### 2.1 推荐架构

采用“后台控制面 + 交互式桌面执行面”的双层架构。后台控制面负责收件、调度、状态、预算和通知；交互式执行面负责 codex exec 与 ChatCut Desktop。首期可全部由 Windows Task Scheduler 拉起，但逻辑上仍保持两层，避免未来迁移到 Windows Service 时重写业务代码。

~~~mermaid
flowchart TD
    A[任务收件箱\n本地 JSON 为默认\nCSV 为批量导入\n在线表格为可选适配器] --> B[Inbox Watcher\n校验 去重 原子认领]
    T[Task Scheduler\n定时唤醒 登录唤醒 启动恢复] --> S[Unattended Supervisor]
    B --> S
    S --> L[现有 pipeline_lock\n加租约与心跳]
    S --> O[Workflow Orchestrator\n复用 pipeline.py local.py process.py]
    O --> C[Codex Executor\ncodex exec 非交互]
    C --> P[需求 素材 分析 中文稿\n本地化 配音 制作 技术复核]
    P --> G{首选剪辑器可用?}
    G -->|是| H[ChatCut Controller\n工具或 MCP 优先\nUIA 仅作次级方案]
    G -->|否且满足降级策略| F[FFmpeg Fallback\nrun_local_batch.py]
    H --> Q[导出验证\n时长 分辨率 音轨 字幕 哈希]
    F --> Q
    O --> APL[Approval Queue\n引用 pipeline-evidence]
    APL --> N[Notification Adapter\n飞书推荐 邮件备份 企业微信可选]
    Q --> D[本机交付区]
    D --> M[员工手动第 07 步发布]
    S --> R[日志 指标 日报 预算熔断]
    R --> N
~~~

### 2.2 关键原则

- **ChatCut 优先**：正常任务必须先尝试 ChatCut；只有达到明确的不可用阈值且任务允许降级时，才调用 **scripts/run_local_batch.py**。
- **状态先于动作**：任何外部动作前先持久化意图、任务版本和 attempt；动作成功后再写输出证据，确保断电后能判断“未开始、进行中、已完成但未登记”。
- **证据驱动幂等**：阶段完成以输入哈希、配置哈希、工具版本、输出哈希和验证结果共同决定，不能只看文件是否存在。
- **批准是真实事件，不是布尔开关**：自动批准只能依据预先授权的政策和已有批准证据推导；不得生成冒充用户签字的 zh-approval。
- **发布硬隔离**：自动化终点为本机交付。发布账号、上传按钮、付费开通和广告投放均不属于可调用能力。
- **可降级但不可静默**：任何 ChatCut→FFmpeg 降级都写入任务状态、日报和通知，成片元数据必须标明 renderer=ffmpeg_fallback。

## 3. 各组件设计

### 3.1 任务收件箱

#### 方案比较

| 方案 | 优点 | 缺点 | 适用性 |
|---|---|---|---|
| 本地文件夹投递 JSON／本地表单生成 JSON | 无账号依赖、离线可用、Windows ACL 可控、易原子写入、易审计、可被 FileSystemWatcher 发现 | 需要定义 schema；员工直接编辑 JSON 的体验一般 | **推荐默认**。本地表单只负责生成 JSON，Supervisor 只消费 JSON |
| CSV | 适合批量任务和运营人员用 Excel 编辑；便于导入导出 | 嵌套字段、素材列表、审批策略和多语言配置表达能力差；并发编辑易产生半文件 | 作为批量导入适配器，导入后转换为标准 JSON，不直接作为运行时真相源 |
| 在线表格 | 多人协作、远程可见、可作为业务看板 | 依赖账号、网络、API 配额和凭据；本任务又明确不接触账号；离线与回执一致性较差 | 后续可选，不作为默认。仅在客户明确授权账号和 API 后增加只读／最小写回适配器 |

#### 推荐协议

默认使用本地目录 **.runtime/unattended/inbox**，但该目录仅在实施阶段创建，本次文档不创建。投递端先写 task-id.partial，再在同一卷内原子重命名为 task-id.json；Watcher 只读取 json 后缀。标准字段至少包括：schema_version、task_id、customer_id、created_at、quantity、market、language、material_paths、allow_collection、creative_requirements、deadline、approval_policy_id、budget_profile_id、preferred_editor=chatcut、allow_ffmpeg_fallback。

认领流程：pending → claimed → accepted／rejected。认领动作必须是同一文件系统内原子移动；任务内容解析后计算 request_sha256。task_id 相同且哈希相同视为重复投递并复用结果；task_id 相同但哈希不同进入 conflict，必须人工决定新版本号，不能覆盖原任务。

### 3.2 调度与 Supervisor

Supervisor 是需新建的长期控制组件，职责仅限于调度、状态和策略，不复制具体生产逻辑：

1. 启动时扫描 RUNNING、RETRY_WAIT、WAITING_APPROVAL 和未完成交付任务，执行崩溃恢复。
2. 使用目录事件发现新 JSON；同时每 1–5 分钟轮询一次，防止文件系统事件丢失。
3. 使用 Task Scheduler 设置开机／用户登录／固定间隔／网络恢复触发器；目录事件仅作为快速唤醒，不作为唯一可靠来源。
4. 获得全局 pipeline_lock 后再派发任务；锁中记录 machine_id、pid、session_id、task_id、acquired_at、heartbeat_at、lease_until。
5. 锁过期时先检查原进程、Codex 子进程、ChatCut 导出和输出证据；只有确认无活跃执行后才能接管，禁止“看到锁旧就删除”。
6. 每次只启动允许数量的任务，默认 ChatCut 并发为 1；下载／分析／TTS 可配置有限并发，但必须受 CPU、GPU、磁盘、API 额度和每日预算共同约束。

### 3.3 Codex Executor

新建 Codex Executor 作为现有 CLI／API／MCP 与 Windows 调度之间的受控启动器。它不让模型自由决定权限，而是把每次运行固定成可审计的执行合同：

- 使用 codex exec 非交互模式；具体命令行参数在实施时按客户机已安装 Codex CLI 版本锁定并回归验证。
- sandbox 设为 workspace-write；approval 设为 never，避免无人值守时弹出无法处理的确认框。该组合只有在 OS 权限和工作目录已经收窄时才安全。
- 每个任务使用独立工作目录或独立可写根，仅允许写该任务目录、规定的运行状态目录和本机交付目录；仓库源码、其他客户项目、账号配置目录保持只读。
- 启动提示由模板生成，包含 AGENTS 约束、任务 JSON、当前 stage-state、已有证据、允许工具、禁止动作、预算剩余和完成条件。
- 子进程 stdout／stderr 逐行写 JSONL；记录 command_digest、model、开始结束时间、退出码、token／费用（可取得时）、超时和杀进程原因。
- 命令白名单不应只靠提示词。使用独立 Windows 自动化账号、NTFS ACL、网络出站规则和包装启动器限制真实能力。
- 明确禁止 Codex 打开紫鸟、TikTok、邮箱、企业微信、飞书客户端和发布页面；通知仅经独立 Notifier 发送预定义消息。

### 3.4 ChatCut Controller

#### 当前真实调用方式

**scripts/prepare_chatcut.py** 当前负责把生产准备结果转换为 ChatCut 可验证的编辑批次，并以 validateOnly 方式确认结构或生成准备证据；**workflow/production/chatcut.py** 与 **workflow/production/preparation.py** 提供 ChatCut 相关的数据准备与生产接口。它们没有把 ChatCut Desktop 变成后台渲染服务。真实编辑、包装、字幕应用和导出仍由交互式桌面会话中的 ChatCut 执行，目前通常是员工通过 Codex 已连接的 ChatCut 工具／MCP 操作并复核。

因此，无人值守不能把“prepare_chatcut 成功”写成“成片已导出”。必须新建 ChatCut Controller，并把“批次准备成功”“ChatCut 已应用批次”“导出完成”“技术复核通过”拆成四个独立状态和证据。

#### 控制方案排序

1. **首选：Codex 已连接的 ChatCut 工具／MCP**。前提是该工具能在 Windows 交互会话中稳定提供：健康握手、打开项目、应用编辑批次、等待操作完成、导出、返回输出路径和错误码。优点是语义级控制强、较少依赖屏幕坐标。实施前必须做能力清单和版本兼容测试，不能根据“能人工调用”推断“能 7×24 自治”。
2. **次选：Windows UI Automation／可访问性接口**。用控件树、窗口标题和 AutomationId 定位，不使用固定屏幕坐标。用于处理启动、项目选择、导出和少量稳定弹窗。风险是版本更新、国际化、焦点、渲染状态和自绘控件可能破坏定位。
3. **最后手段：视觉／坐标自动化**。只可作为已知版本的短期兜底，必须配截图证据、分辨率锁定和失败即停；不应成为正式 7×24 方案。
4. **不可取：直接改写 ChatCut 私有项目文件或内部数据库**。除非获得官方稳定格式和授权，否则升级风险、数据损坏和不可审计性过高。

#### 健康检查分层

##### 2026-10-17 Mac 实测（阶段 0.5 已落地）

> 日期口径：北京时间 2026-10-17。本节记录真实 Mac 验证，并限定本阶段只实现健康检查与保守重启，不代表完整无人值守栈已完成。

**实测证据**

1. 重启前，ChatCut 已连续打开 2 天以上：所有项目级 MCP 操作均在 30 秒超时，get_active_project 返回陈旧项目，list_projects 约 30 秒仍无正常响应。说明“ChatCut 进程存在”不能作为健康证据。
2. 用户执行 Cmd+Q 后重新打开 ChatCut，全路径恢复：list_projects 约 0.3 秒；随后 duplicate_project → target_project → edit caption → export 1080p 渲染约 5.5 秒，ffprobe 校验通过。原项目未修改；测试副本 TEST-无人值守-20261017 保留在 ChatCut。成片为 /tmp/chatcut-test-20261017/out2/TEST-无人值守-20261017.mp4。
3. Codex 易把 ChatCut 工具参数格式传错，尤其 edit_captions 必须包含 json 字段；每次 exec 若加载全部 MCP，约产生 16 万 input token，需要 chatcut-only 瘦身 profile。MCP 工具有时第一轮未加载，应先重建/重试只读健康探针，不能直接进入编辑。
4. 本次只证明“用户手动退出并重开后恢复”。ChatCut 进程在完全无用户介入时的自动重启尚未完成真实证明，因此 --apply 仍是显式开关，默认 dry-run。
5. Windows 版 ChatCut 存在但未验证；本阶段只落地 macOS。ChatCut 本地导出不耗 credits，但运行时必须保持登录且在线；自动更新可能打断 MCP，应纳入运行窗口和恢复记录。

**健康探针定义**

- 权威判定：通过本机 ChatCut MCP 启动器，以 stdio JSON-RPC 完成 initialize → tools/call，调用 list_projects 或 read_project 一类只读轻量工具，并在阈值内返回。默认阈值为 10 秒，可由 CLI --timeout 调整。
- 进程、socket 或启动器存在只能作为辅助诊断；只要轻量 MCP 调用超时或报错，即判定不健康。今日实测已证明“进程存在但 MCP 假死”。
- 探针禁止 submit_*、删除项目、导出大片及其他修改型工具。默认报告字段包含 status、latency_ms、reason、would_restart；健康退出码 0，不健康退出码 2，用法错误退出码 1。

**macOS 重启流程**

1. 仅在明确传入 --apply 且探针判定不健康时执行；默认只输出 JSON dry-run 报告。
2. 优先用 AppleScript 优雅退出：tell application "ChatCut" to quit，等待主进程退出；超时后只对精确主进程名 ChatCut 发送温和 SIGTERM，不得杀无关进程。
3. 执行 open -a ChatCut，轮询只读 MCP 探针，直到就绪或达到重启超时。
4. 可选 --reopen-project <name|id> 只能在 MCP 恢复后调用 target_project；实现先通过 tools/list 读取当前 inputSchema，再选择已存在的 name/id 字段，不臆造完整 schema，不得删除、覆盖或改动其他项目。
5. 建议在长时间批处理开始前或每天低风险窗口做一次预防性重启，并避开 ChatCut 自动更新；是否启用须结合当天任务、登录在线状态和恢复证据。


## Codex chatcut_desktop MCP 可见性（2026-10-19）

**根因**：无人值守 profile 把 `CHATCUT_MCP_CLIENT` 设成了 ChatCut 0.6.13 不接受的 `codex_unattended`，`chatcut-mcp` 启动即 fatal，Codex 注册到 0 个 MCP 工具；同时 `gpt-5.6-sol` 默认 defer MCP 且 `tool_search` 已移除，若 `code_mode_host=false`，即便 MCP 起来模型也看不到工具，于是回退 Computer Use / 应用内 AI Agent（烧 credits）。

**修复**：
1. `CHATCUT_MCP_CLIENT = "codex_app"`（与主 config 一致；非法值含 `codex_unattended`、`codex_cli`）。
2. `features.code_mode_host = true`；producer 启动 Codex 时强制 `--enable code_mode_host --disable computer_use`。
3. 新增 `workflow/unattended/codex_mcp_gate.py`：制作前用**同一套配置 env** 拉起 chatcut-mcp 做 tools/list 门禁，失败则 fail-fast，不再只依赖「不带 client env 的」ChatCut 健康探针。

**验证**：`codex exec -p unattended-chatcut` 下 `mcp__chatcut_desktop__list_projects` 出现在 ALL_TOOLS 并可返回项目列表。

**Codex MCP profile 与 skill/prompt**

- 建立仅加载 chatcut_desktop 与必要本地校验工具的 chatcut-only profile，避免每轮加载全部 MCP 造成约 16 万 input token，并降低首轮工具未加载概率。
- 固化顺序：健康检查 → list_projects → 必要时 duplicate_project → target_project → 编辑 → export → ffprobe。始终保留原项目和测试副本。
- edit_captions 参数必须包含 json 字段；export、target_project、list_projects、duplicate_project 均以当前工具返回 schema 为准，不凭记忆拼参数。
- 不使用 submit_* 作为无人值守主路径。

**实现边界与开放问题**

- 已落地：workflow/chatcut/health.py、scripts/chatcut_health.py 和 mock 单测；启动器解析顺序为 $CHATCUT_MCP，其次 macOS ~/Library/Application Support/ChatCut/chatcut-mcp。仓库不复制也不记录启动脚本中的 invocation capability，仅只读执行本机脚本。
- 未完成：真实无用户介入的 macOS 自动退出/重启证明、ChatCut 自动更新期间的可靠恢复、Windows 重启与探针路径。
- Windows 当前必须明确返回“阶段 0.5 未验证/未实现”，不得假装与 macOS 等价。


- L0 机器：自动化用户已登录、桌面会话可交互、未休眠、磁盘空间充足。
- L1 进程：ChatCut 进程存在、主窗口可见、CPU／内存未持续异常、无崩溃恢复对话框。
- L2 控制通道：ChatCut 工具／MCP 握手成功，版本在允许范围，能读取当前项目状态。
- L3 功能：validateOnly 批次成功，能创建临时项目或加载指定任务。
- L4 金丝雀：每日首次任务前导出 2–5 秒无客户数据的本地测试片，校验容器、分辨率、音轨和耗时。

#### 自愈与退避

单次工具调用超时后先重连控制通道；第二次失败关闭当前任务项目并重开；第三次失败优雅退出 ChatCut 后重启；仍失败则进入 CHATCUT_UNAVAILABLE。退避建议 1、5、15、30 分钟并加入抖动，连续失败上限默认 4 次／任务、8 次／日。检测到登录失效、版本强制更新、许可提示、系统弹窗或项目损坏时不得盲点确认，立即转人工。

### 3.5 FFmpeg 降级策略

FFmpeg 路线复用 **scripts/run_local_batch.py**，但只有同时满足以下条件才能自动降级：任务 JSON 明确 allow_ffmpeg_fallback=true；ChatCut 达到不可用阈值；任务不依赖仅 ChatCut 原生可实现的字幕／贴纸／模板；降级后仍能满足已确认中文稿和质量标准；预算与截止时间允许。

降级时必须：

- 写 degraded_reason、chatcut_attempts、fallback_started_at、renderer_version。
- 给员工发送“已降级”通知，列出缺失或变化的包装能力。
- 输出文件名、交付清单和日报标明 FFmpeg 降级，不与 ChatCut 成片混计验收。
- 若客户要求必须 ChatCut，则任务停在 BLOCKED_CHATCUT，不生成替代品冒充完成。

### 3.6 批准队列

批准队列是新组件，但证据规则沿用现有 pipeline-evidence／zh-approval：

- 中文稿首次批准、原意／卖点／时长／镜头逻辑／可见文字／语音方案的实质改动，必须等待对应客户审核人批准。
- 当地语言稿在保持已批准中文原意时，由内部本地化复核通过，不伪装成用户审阅外语。
- 音色可依据客户自己的 voice_approval 文件、绝对路径和 SHA-256；仅复用同一客户、同一市场、未过期且仍在批准池的音色时可自动通过。
- 自动批准写 policy_decision 证据，内容是“根据 policy_id 和已有批准证据自动放行”，而不是伪造新的 user_approved=true。
- 任何模板、音色、包装或文案超过批准范围，转 WAITING_APPROVAL，并把差异摘要、中文预览、关联任务和截止时间加入通知队列。
- 通知超时不改变批准结果。建议 4 小时首次提醒、24 小时升级、每日汇总；任务保持可恢复，不占用 ChatCut 锁和执行槽。

### 3.7 通知方案

| 渠道 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 邮件 | 通用、可归档、适合日报和长附件 | 即时性和交互性弱，容易被过滤；SMTP／OAuth 凭据管理复杂 | 作为审计备份和每日报告渠道 |
| 企业微信机器人 | 中国企业常见、消息触达快、群通知方便 | 机器人能力和互动回执受企业配置限制；客户未必使用企业微信 | 客户已统一使用时可选 |
| 飞书机器人 | Webhook／签名、富文本卡片、按钮和线程体验较好，适合批准摘要与状态卡片 | 需要飞书租户、机器人授权和凭据；按钮回执仍需服务端验签与幂等 | **推荐默认通知渠道**，前提是客户明确授权；邮件作为失败备份 |

Notifier 与生产执行器分离，只接收结构化事件。消息发送失败写队列并重试，不回滚已完成生产阶段。批准回执必须带 approval_request_id、actor、timestamp、decision、comment 和签名验证结果，再转换为 pipeline-evidence；不能仅凭聊天文本“看起来像同意”自动批准。

### 3.8 日志、指标、日报、预算和并发

- 日志分为 supervisor.jsonl、task-events.jsonl、codex.jsonl、chatcut.jsonl、notification.jsonl；所有记录包含 task_id、stage、attempt、correlation_id、machine_id 和时间。
- 指标包括队列长度、等待批准数量、阶段耗时、ChatCut 可用率、导出成功率、重试次数、降级次数、缓存命中／哈希复用率、磁盘余量、模型 token、TTS 字符／分钟和估算费用。
- 每日报告按真实墙钟时间统计，不把并行步骤相加冒充总耗时；区分新任务、缓存恢复、客户等待、服务等待和开发／运维排错。
- 预算配置至少包含 per_task_model_cost、per_day_model_cost、per_task_tts_cost、per_day_tts_cost、task_wall_clock_limit、daily_active_minutes、max_chatcut_exports、max_collection_download_bytes。
- 达到软上限时提醒并停止启动新阶段；达到硬上限时把任务转 BUDGET_BLOCKED。已完成且正在原子落盘的输出允许收尾，但不得继续产生付费调用。
- 默认并发：ChatCut 1、导出 1、Codex 重型任务 1；下载／静态分析／TTS 可各 2，最终由资源监控动态下调。相同客户或共享素材库的写操作继续受项目级锁保护。

### 4.2 状态机扩展

建议在现有任务状态机外增加无人值守控制状态，不替换已有业务 stage：

~~~mermaid
stateDiagram-v2
    [*] --> DISCOVERED
    DISCOVERED --> VALIDATING
    VALIDATING --> REJECTED: schema或路径不合法
    VALIDATING --> READY: 合法且无需前置批准
    VALIDATING --> WAITING_APPROVAL: 缺中文稿或音色等批准
    WAITING_APPROVAL --> READY: 收到真实证据或政策自动放行
    READY --> CLAIMED
    CLAIMED --> RUNNING
    RUNNING --> RETRY_WAIT: 可恢复失败
    RETRY_WAIT --> RUNNING: 到next_retry_at
    RUNNING --> BLOCKED: 登录 更新 许可 预算或人工决策
    BLOCKED --> READY: 阻塞解除
    RUNNING --> DEGRADED: ChatCut转FFmpeg
    RUNNING --> QA
    DEGRADED --> QA
    QA --> REWORK: 技术或内容复核失败
    REWORK --> RUNNING
    QA --> LOCAL_DELIVERED
    LOCAL_DELIVERED --> MANUAL_PUBLISH_PENDING
    MANUAL_PUBLISH_PENDING --> [*]
~~~

MANUAL_PUBLISH_PENDING 是自动化终态，不触发第 07 步。RUNNING 内部继续使用现有阶段状态，例如素材检查／采集、分析、中文稿、本地化、配音、ChatCut 准备、编辑、导出、技术复核和本机交付。

### 4.3 stage-state 最小字段

每个阶段记录：stage_name、status、input_hashes、config_hash、tool_name、tool_version、attempt、started_at、heartbeat_at、ended_at、next_retry_at、exit_code、output_paths、output_hashes、validation_result、evidence_refs、approval_refs、cost_actual、wall_clock_seconds、worker_id、session_id、degraded_reason、error_class、error_digest。

恢复判定顺序：

1. 验证状态文件能解析且 schema_version 兼容。
2. 若 status=SUCCEEDED，重算关键输出哈希并运行轻量技术验证；一致则复用。
3. 若 status=RUNNING 但心跳过期，检查子进程、ChatCut 导出和临时文件；能够证明完成则补登记，否则转 RETRY_WAIT。
4. 若输入或配置哈希变化，只失效受影响阶段及其下游，不清空整条任务。
5. 重试前保存上次错误摘要；同一 error_digest 连续出现达到阈值后转 BLOCKED，避免无限循环。

## 5. 失败与恢复矩阵

| 故障 | 检测 | 自动动作 | 何时转人工 | 保留证据 |
|---|---|---|---|---|
| 收件 JSON 不合法 | schema、编码、路径校验失败 | 移入 rejected，不进入流水线 | 立即通知提交人 | 原文件哈希、错误字段、解析日志 |
| task_id 冲突 | 相同 ID 不同 request_sha256 | 移入 conflict，禁止覆盖 | 必须决定新版本或撤销 | 两个请求哈希与来源时间 |
| pipeline_lock 被占用 | 锁未过期且心跳正常 | 排队等待，不启动第二流水线 | 超过任务 SLA | 锁持有者、心跳、等待时长 |
| 陈旧锁 | 租约过期 | 检查 PID、会话、ChatCut 和输出后接管 | 状态互相矛盾时 | 接管检查清单和旧锁快照 |
| codex exec 非零退出 | 退出码／超时／stderr 分类 | 可恢复错误按 1、5、15 分钟退避；复用已成功阶段 | 同一错误 3 次或权限／策略错误 | 命令摘要、模型、日志、费用 |
| 素材缺失或不可读 | 路径、哈希、媒体探测失败 | 若允许采集则只补缺口；否则 WAITING_INPUT | 无允许来源或素材仍不足 | 缺料清单、探测结果 |
| 采集源失败 | HTTP／解析／配额失败 | 换已授权来源、断点续传、退避 | 需账号、验证码或扩大授权时 | URL／来源、状态码、重试记录 |
| 中文稿未批准 | 无有效 zh-approval 证据 | 入批准队列，释放执行槽 | 到提醒 SLA，不自动伪造批准 | 请求版本、差异摘要、通知回执 |
| 音色无有效批准 | voice_approval 缺失、哈希不符或市场不匹配 | 生成试听请求，不继续真实配音 | 客户未批准新池 | 候选音色、试听文件哈希 |
| TTS 暂时失败 | 服务错误、空音频、时长异常 | 同音色同参数重试；不重新随机 | 达重试或费用上限 | 请求摘要、音色、音频验证 |
| ChatCut 控制通道断开 | MCP／工具握手失败 | 重连→重开项目→重启 ChatCut→退避 | 登录、许可、更新弹窗或连续失败 | 健康快照、截图／窗口树、版本 |
| ChatCut 卡死 | 心跳、窗口无响应、阶段超时 | 保存可得状态，终止当前尝试，重启后从 stage-state 恢复 | 项目反复损坏 | 进程指标、超时阶段、项目副本指针 |
| ChatCut 导出失败 | 无输出、文件仍增长、容器不可读 | 清理本次临时输出后同项目重试 | 两次同位置失败或磁盘异常 | 导出设置、临时文件、错误码 |
| 强制更新／弹窗 | 版本变化、未知模态窗口 | 停止点击，标记 CHATCUT_UPDATE_BLOCKED | 立即 | 窗口标题、截图、旧新版本 |
| 技术复核失败 | ffprobe／媒体规则／字幕音轨检查不合格 | 只重做受影响阶段；ChatCut 与 FFmpeg 分开统计 | 连续两次相同失败 | 检查项、阈值、输出哈希 |
| ChatCut 降级 | 达不可用阈值且任务允许 | 调用 run_local_batch.py，标记 degraded | 不允许降级或质量无法等价 | 原因、尝试次数、能力差异 |
| 通知发送失败 | Webhook／SMTP 错误 | 本地队列退避重试，切备份渠道 | 两渠道均失败超过 24 小时 | 消息哈希、渠道、回执 |
| 达到预算上限 | Budget Guard 预估或实际超限 | 停止新付费阶段，转 BUDGET_BLOCKED | 必须提高额度或取消任务 | 已用／剩余额度、估算依据 |
| 断电／系统重启 | Supervisor 启动扫描 | 重建队列、校验锁、核对输出哈希后续跑 | 状态／输出矛盾 | 启动恢复报告 |
| 磁盘不足 | 预检与持续监控 | 停止新下载／导出，清理仅可再生临时文件 | 低于安全线且无可清理项 | 磁盘快照、清理清单 |

## 6. 安全与权限

### 6.1 Windows 身份与凭据

- 建议创建专用本地自动化账号，不使用管理员日常账号。该账号只访问仓库只读区、指定任务工作区、素材目录、ChatCut 必要配置和本机交付目录。
- 凭据优先使用 Windows Credential Manager 或 DPAPI 绑定到自动化账号；配置文件只保存 credential_ref，不保存明文 token。
- 飞书／企业微信／邮件凭据与生产凭据分开；通知适配器只能发预定义消息，不能读取员工聊天或邮箱。
- ChatCut 登录态若必须存在，应绑定专用账号并由人工首次登录；Supervisor 只检测“有效／失效”，不得记录密码或自动绕过 MFA。
- 日志默认脱敏路径中的客户名、token、邮箱、手机号和 URL 查询参数；原始错误仅存受限目录并设置保留期。

### 6.2 codex exec 防越权

- approval=never 只表示不弹交互批准，不代表无限权限；必须配合 workspace-write、受限 cwd、NTFS ACL、独立账号和出站防火墙。
- 默认拒绝访问浏览器资料目录、紫鸟、TikTok、邮件客户端、企业微信／飞书客户端、系统凭据目录和其他客户项目。
- 网络只允许经过批准的模型、TTS、素材源和通知端点；未知域名默认拒绝。需要新增域名时走人工变更。
- 付费动作由 Budget Guard 前置授权；模型、TTS、素材服务均有单任务和每日硬上限。系统不得自动开通套餐、充值或升级。
- 生产提示中明确列出禁止动作，但最终安全依靠系统权限，而不是依靠提示词自律。
- 本机交付后写只读 manifest；第 07 步发布由员工从交付区选取，自动化不持有上传工具和账号。

### 6.3 审计与数据隔离

每次任务建立 correlation_id；任何状态变化、批准引用、外部调用、降级、重试和人工解除阻塞都写 append-only 事件。不同客户任务目录使用 ACL 隔离；共享素材库只读，新增素材先进入隔离区完成媒体和来源检查后再晋级。证据、日志和交付物设置独立保留期，删除操作必须由人工维护流程执行，Supervisor 不自动删除客户原始素材。

## 7. Windows 部署选择

### 7.1 Windows Service 与 Task Scheduler 对比

| 维度 | Windows Service | Task Scheduler |
|---|---|---|
| 无人启动 | 强，开机即可运行 | 强，可用开机、登录、定时、事件触发 |
| 交互式桌面 | 弱。服务位于 Session 0，不能可靠控制 ChatCut GUI | 强。选择“仅在用户登录时运行”可进入交互会话 |
| 权限与运维 | 适合后台 watcher、日志和队列；安装和升级较重 | 部署简单、客户可见、适合首期验证 |
| ChatCut 重启 | 不能直接安全操纵用户桌面 | 可在专用登录会话内启动和监控 ChatCut |
| 崩溃恢复 | 服务恢复策略成熟 | 可设置失败重启和重复计划，但需应用自身心跳 |
| 推荐角色 | 后续作为后台控制面 | **首期默认方案和 ChatCut Worker 的长期方案** |

### 7.2 推荐部署拓扑

首期全部使用 Task Scheduler：

- Unattended Supervisor：用户登录时启动，失败后 1 分钟重启；另设每 5 分钟兜底触发，程序自身通过单实例锁退出重复实例。
- Startup Recovery：系统启动后延迟 2 分钟运行；若自动化用户尚未登录，只做状态标记和通知，不尝试 GUI。
- ChatCut Worker：仅在专用自动化用户登录时运行，按任务由 Supervisor 拉起。
- Daily Report：每天固定时间聚合并入通知队列。

成熟后可把 Inbox Watcher、预算、日志和通知迁移到 Windows Service，但 ChatCut Worker 仍留在交互式会话，通过本机命名管道／localhost 且带 ACL 的接口接收任务。不要启用“服务与桌面交互”的旧式方案。

### 7.3 会话、电源和更新要求

- 需要专用自动登录账号或人工确保登录；自动登录本身有凭据风险，客户必须明确接受，并通过 BitLocker、物理访问控制和最小权限降低风险。
- 锁屏通常仍保留会话，但部分 GPU／UI 自动化在远程桌面断开、分辨率变化或安全桌面弹窗下会失败，必须做实机验证。禁止以“永不锁屏”代替安全设计。
- 禁用睡眠和休眠，显示器可关闭；高性能／平衡电源策略按渲染稳定性验证。
- Windows Update 设维护窗口；重启前 Supervisor 停止接新任务，等待安全点或写恢复状态。重启后运行启动恢复。
- ChatCut 自动更新应关闭或限定人工维护窗口；版本升级先在金丝雀任务验证 validateOnly、真实编辑、导出和 UI 定位，再放行生产。
- 远程桌面断开可能改变桌面尺寸或会话；优先使用保持本地控制台会话的运维方式，并锁定分辨率、缩放和语言。

## 阶段 1：精简版已落地（2026-10-17）

本次按阶段 1 的最小控制面收敛实现，只负责本地 JSON 收件、ChatCut 只读健康探针、单并发认领、复用现有 create/plan-batch 登记以及状态落盘。不会调用 pipeline run、ChatCut submit/export、发布或账号能力。

### 实际目录

```text
.runtime/unattended/
  inbox/
    incoming/      # 投递落点，也可理解为 pending；仅识别 *.json
    processing/    # 原子 rename 后的已认领任务
    done/          # 已创建 workflow job 或同哈希重复投递
    failed/        # schema、媒体路径或 create 失败
    conflict/      # 同 task_id 不同 request_sha256
  tasks/<task_id>/
    request.json
    state.json
  locks/supervisor.lock
```

默认数据根为项目 `.runtime`；设置 `WORKFLOW_DATA_DIR` 后改用该目录。目录由 `workflow.unattended.inbox.Inbox` 首次运行时创建。测试全部使用临时目录，不读取真实业务库。

### 阶段 1 JSON schema

必填字段：`title`、`product`、`market`（MX/BR/ID/PH）、`count`（1–100）。可选字段：`style`、`notes`、绝对路径数组 `media_paths`、`task_id`、`schema_version=1`、`concepts`（若提供须对齐现有 plan-batch ConceptInput：ordinal/angle/hook/buyer_concern/proof_requirement/cta_direction，可选 source_asset_ids；create 成功后登记，失败会保留已创建的 workflow_job_id）。缺少 task_id 时按规范化请求生成稳定编号；媒体路径存在性在处理时校验。enqueue 先写 `*.partial`，fsync 后原子 rename 为 `*.json`。

同一 task_id 与相同规范化 SHA-256 视为重复，不再次 create；同 task_id 不同哈希移入 conflict 且不覆盖原任务。锁同时使用操作系统文件锁和包含 pid、acquired_at、heartbeat_at、lease_until、task_id 的租约元数据；只有进程不存在且租约已过期才接管异常遗留锁。

### CLI

```bash
.venv/bin/python scripts/unattended.py enqueue --file /绝对路径/request.json
.venv/bin/python scripts/unattended.py once
.venv/bin/python scripts/unattended.py list
.venv/bin/python scripts/unattended.py watch --interval 30
```

`once` 每次最多处理一条；`run` 是 once 的兼容别名。健康探针不通过时不会认领，也不会自动 apply/restart；应先单独运行现有 chatcut_health 排查。

### 与完整设计的差异和延后项

- CSV 导入器延后到后续阶段。
- processing 遗留任务的完整租约恢复扫描延后；本阶段保留崩溃安全单实例锁和清晰状态文件。
- Windows Task Scheduler 安装器延后；本阶段只提供周期调用说明。
- Codex exec 驱动全制作链、真实媒体导入、pipeline run、ChatCut 制作/导出、通知、飞书和发布均不在阶段 1。

### 周期调用说明（不自动安装）

macOS 可在客户自行维护的 launchd plist 中，把 ProgramArguments 指向项目 `.venv/bin/python`、`scripts/unattended.py`、`once`，并通过 StartInterval 设置周期；WorkingDirectory 设为项目根，按需设置 WORKFLOW_DATA_DIR。本文不创建或加载 plist。

Windows 可在 Task Scheduler 中新建普通定时任务，程序选择虚拟环境的 `python.exe`，参数为 `scripts\unattended.py once`，起始目录为项目根，并按需设置 WORKFLOW_DATA_DIR。本文不提供安装器，也不注册计划任务。

## 阶段 2：精简 MVP 已落地（2026-10-17）

在阶段 1 收件箱之上，增加可选制作工人：`once --produce` / `watch --produce`。

### 行为

1. create（及可选 plan-batch）成功后，若开启 `--produce`：再探针 ChatCut → 写 `unattended_auto_approve` 审计 → `codex exec -m 6a -p unattended-chatcut`（profile 见 `config/unattended-chatcut.config.toml`）按锁定提示驱动 ChatCut 导出。
2. 导出复制到 `unattended/tasks/<task_id>/delivery/`；成功状态 `produced`（done 桶）；失败 `produce_failed`（failed 桶），保留已创建的 `workflow_job_id`。
3. **默认关闭制作**，避免误烧 token / 误改工程。
4. FFmpeg 仅 `--allow-ffmpeg-fallback`；MVP 尚未接线 `run_local_batch`，开启后仍会明确失败并标记 `renderer=ffmpeg_fallback` 意图，禁止静默降级。
5. 不做飞书、发布、预算日报、完整逐条杀进程恢复（完整阶段 2/3/4 仍延后）。

### 风险

- Codex/ChatCut token 与耗时；MCP 首轮偶发未加载；须保持 ChatCut 登录在线。
- 模型渠道：worker 默认 `-m 6a`，若渠道不可用会制作失败。
- 自动放行仅策略审计，事后抽查；勿与真人 zh-approval 混淆。
- 误操作风险：提示词禁止 delete/submit/发布，但仍依赖模型遵守。

## 2026-10-19 补充：禁止 ChatCut 应用内 AI Agent

- 事故：一次 `codex exec` 会话没能加载 chatcut_desktop MCP 工具，Codex 改用 Computer Use 往 ChatCut 应用内 AI Agent 面板里输入提示词。该面板由 ChatCut 托管模型执行（agent.log：provider=bedrock），**消耗 ChatCut 账户额度**（本次日志 cost≈0.309，耗时 74.7s）。
- 规则：无人值守制作只允许直连 chatcut_desktop MCP（create_project/push_asset/edit_item/edit_track/preview_timeline/export/track_progress 等），禁止应用内 AI Agent、禁止 Computer Use 操作 ChatCut、禁止 submit_*。
- 实现：`producer.FORBIDDEN_INAPP_AGENT_RULES` 前置拼接到所有制作 prompt（含自定义模板）；制作结束后 `detect_inapp_agent_runs()` 扫描 `~/Library/Application Support/ChatCut/logs/agent.log`，运行期间若出现内置 Agent 调用，就判 `produce_failed`（renderer=chatcut_inapp_agent），导出留存供复核，并写 `logs/inapp-agent-violation.json`。`ProduceOptions(forbid_inapp_agent=False)` 可关闭。
- 未解决：codex exec code-mode 下 MCP 工具不可见的根因待查；在那之前，确定性的直连 MCP 脚本（见 demo `mcp-direct/build.py`）是更可靠的路径。

| 采集-下载校验 | yt-dlp（优先 H.264）→ ffmpeg 探测（竖屏 h ≥ 1.5w、5–300 s、TikTok 提取器且 id 一致、禁库存域名）→ 规范化 H.264 + faststart → 4×2 联系表；清单 `collection/footage/collection.json`（含每条失败原因） | 合格素材 < 3 → 失败，不使用库存/样例素材顶替 |
| 剪辑导出 | Codex gpt-5.6-sol + chatcut_desktop MCP，模板 `prompts/chatcut_produce.md`（含素材清单、MCP 参数示例、字幕 MG 示例 `prompts/examples/captions_mg_example.jsx`） | 超时/非零退出 → 失败 |
| 成片校验 | `verify_output.py`：竖屏 H.264 ≥720p、8–60 s、无口播须静音（峰值 ≤ -60 dB 或无音轨）、footage_used ⊆ 采集清单、非 TEST 工程、事件日志无 submit_*/search_stock_media/import_url/delegate_task/Computer Use；另查 agent.log 无应用内 AI 运行 | 任一不满足 → 失败，不进 delivery |

各阶段耗时写入 `state.json` 的 `produce.stages`。回归：E2E run1 中 canary 模板把 TEST 工程导出记为 produced（假阳性），现由 `test_producer_production_mode_rejects_canary_export` 覆盖。

## 剪辑前质量门禁 + 导出后自动复核（2026-10-19 run3 后）

run3 成片导出后才发现三处内容问题：混入带底座的台式料理机（AURA）、镜头带原片烧录文字（“Great get-lean breakfast”）、结尾 CTA 是海边人像生活方式镜头。现改为**剪辑前拦截 + 导出后复核 + 自动重剪**：

1. **视觉初筛（剪辑前，`vision.screen_clips`，模板 `prompts/footage_screen.md`）**：每条入库素材在 0～(时长−3s) 均匀抽 12 帧拼成 4×3 图，`codex exec -i <图>`（gpt-5.6-sol、read-only、禁用 ChatCut MCP）逐条判断：
   - 同款形态：杯/瓶类请求要求“杯身即机身”，装在独立电机底座上的（含小型无线款）一律淘汰；
   - 逐帧：商品可见/突出、原片烧录文字（none/small/heavy + 区域 + 裁切后商品是否完整）、水印、纯生活方式；
   - 只有“商品可见 + 无水印 + 非生活方式 + 无烧录文字（或文字在上/下 1/4 且可裁掉）”的帧组成 `usable_segments`（带 `crop: null/top/bottom` 与 `product_prominent`）；
   - 淘汰原因写入 `collection/footage/collection.json`（`candidates[].status=screened_out` + `failure_reason`，`screened_out[].screening`）；
   - 门槛：同款合格 ≥2 条、可用片段 ≥12s、商品突出片段 ≥2，否则采集阶段失败，不进入剪辑。
2. **剪辑约束（`prompts/chatcut_produce.md`）**：只把合格素材及其 usable_segments 交给剪辑 Codex；每个镜头必须完整落在可用片段内；开头与结尾 CTA 必须用 product_prominent 片段；crop 片段用 1.35 倍手动放大把文字推出画布。结果 JSON 必须给 `shots`。
3. **导出后复核（`vision.check_shots` + `vision.review_export`，模板 `prompts/export_review.md`）**：
   - 确定性检查：shots 都在可用片段内，开头/结尾在突出片段；
   - 视觉复核：成片每个镜头中点抽 1 帧，检查同款形态、原片烧录文字（忽略我们自己的字幕与 CTA 按钮）、水印、生活方式镜头、开头/结尾商品是否清楚。
4. **自动重剪**：校验或复核不通过 → 把问题清单反馈给剪辑 Codex，在**同一工程**上修改并导出到 `-r1/-r2.mp4`，最多重剪 1 次（`ProduceOptions.review_retries`，默认 1；错品/原片烧录文字不重剪、直接换素材）；仍不通过则任务失败、不交付。各次耗时记录在 `state.json → produce.stages`（`produce/verify/review`、`produce_r1/verify_r1/review_r1`…）。
5. **补充检索（run6 后新增）**：初筛累计不达标时不立即失败，而是带着淘汰原因（如“装在独立底座上的台式料理机”）和已用视频 ID 让 Codex 换更精确的检索词再找一轮，只下载、初筛新候选，累计合格素材达标即进入剪辑；默认最多 3 轮（`collect_footage(discover_rounds=3)`），仍不足则失败，绝不用不合格或库存素材顶替。run6 实测：首轮 10 条里 9 条被正确淘汰（AURA/Ninja/台式离心榨汁机/普通水杯/满屏字幕），只剩 1 条合格。

## 采集加速（2026-10-19）

墙钟时间主要耗在 Codex `web_search` 检索（实测单轮常 280–900s；形态不符时会再跑第 2 轮，合计可到 ~800s+）。已做：

1. **形态词首搜**：`discover_speed.infer_form_hints` 按商品（便携榨汁杯 / 清洁刷等）预填形态定义与推荐查询，写进 `tiktok_discover.md` 的 `{{form_hints}}`。
2. **检索预算**：提示词要求有限次 `web_search`；早停门槛 `discover_min_urls` 随批次候选预算抬高（约 8–20），凑齐即输出 JSON（榨 web 后）。
3. **种子缓存**：`config/discovery-seeds/<市场-商品>.json`；同商品再次采集先下载种子，初筛够用则 **跳过 Codex 检索**（金丝雀：8 条种子约 3.3s，discovery_calls=0）。
4. **错误形态软过滤**：候选 why/evidence 已写明 countertop/底座 等则跳过下载。
5. **重连中止**：事件流出现 `Reconnecting... ≥3/5` 时杀掉 Codex（exit 99），避免空转。
6. **并行下载**：yt-dlp 默认 4 工人。
7. **默认超时**：发现超时 900→**480s**；默认轮次 3→**2**。

质检门不变：同款形态、烧录字、开头/结尾商品清楚、无 BGM、只用 MCP 直连。

## 榨 web（squeeze-web，2026-10-23）

在 **不接 App 站内搜 / 不换商用数据源** 的前提下，尽量多捞公开网页上的 TikTok URL（仍是 Codex `web_search` → yt-dlp）：

1. **眼霜词模板**：`eye_cream` 增补西/葡/印尼本地说法 + 涂抹/上脸动作词；镜像仍只用仓内已有的 tikwm / urlebird（外加 `"tiktok.com/@…/video/"` 直链检索），不引入新下载站。
2. **预算**：`discover_min_urls(max_candidates)` 随批次抬高早停门槛（原硬顶 10；现约 10–20）；`count≥8` 时 `discover_rounds` 上限 6→7、`max_searches` 基数 +1。质检门不变。
3. **美妆首轮扩区**：`eye_cream` / `lip_balm` 第 1 轮即 MX/BR/ID/PH 全区检索（口播/字幕仍跟交付市场）。

**预期**：相对 `3ec1e06` 修好早停后的 web 基线，合格独特 URL 大约 **+20%–50%**，墙钟可能多 5–15 分钟；**不会**变成 TikTok App 站内搜的素材池。
